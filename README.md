# VexOS

VexOS is a small educational x86_64 operating system project that boots via an EFI bootloader and runs a minimal kernel with a simple desktop environment. It includes basic kernel subsystems (PMM, VMM, heap, tasking), PCI/xHCI support, a SimpleFS persistent storage image, and a fullscreen setup wizard.

## Key features
- EFI bootloader (src/boot) that loads kernel.elf and passes a BootInfo struct
- Kernel core (src/kernel/core): framebuffer console, PMM (physical memory manager), VMM (virtual memory), heap, PCI enumeration and drivers (xhci), simple desktop UI and setup wizard
- SimpleFS persistent storage image (dist/storage.img) and image embedding helper in run.sh

## Development roadmap

See [`docs/ROADMAP.md`](docs/ROADMAP.md) for the full plan to reach a general-purpose operating system, including verified progress and remaining work. The VFS foundation now supports hierarchical paths over SFS1, implicit directory iteration, reference-counted open nodes, and create/unlink APIs. SFS1 still has a 31-byte path limit and append-only data allocation, so deletion does not reclaim disk sectors. See [`docs/VFS_DESIGN.md`](docs/VFS_DESIGN.md) for architecture, limitations, and the next storage milestones.

## Prerequisites
- GNU toolchain: gcc, ld, objcopy, make
- mtools (mformat, mmd, mcopy) for writing the EFI image
- qemu-system-x86_64 and OVMF (UEFI firmware) for running the VM
- python3 (optional) used by run.sh to embed new.png into dist/storage.img

## Build
Run:

    make

The normal build produces `dist/BOOTX64.EFI`, `dist/kernel.elf`, the bootable FAT image `dist/tiny64.img`, and the separate persistent data image `dist/storage.img`.

DoomGeneric is kept in `src/doom` as a pinned upstream submodule. It is **not**
built by the kernel Makefile: it is a separate user-mode ELF with a VexOS
platform backend. The launcher looks for the IWAD at the canonical SimpleFS
name `doom.wad`; the source file can be the registered game's `DOOM.WAD`,
shareware `DOOM1.WAD`, or another compatible IWAD.

To build the Doom app and prepare storage with your own IWAD:

```sh
make doom
make doom-storage WAD=/path/to/DOOM.WAD
```

The packer validates the IWAD header and directory, then stores it as
`doom.wad` alongside `doom.elf`. The WAD stays outside the repository; local
`.wad` / `.WAD` files are ignored by Git. The desktop's `doom` / `ring3`
command launches the user-mode app. The CI playtest continues to use
Freedoom as its redistributable test IWAD, but it is packed under the same
`doom.wad` runtime filename. Do not use the old `BUILD_DOOMGENERIC=1`
option; it was a no-op placeholder, not a working port.

## Run (development)
run.sh builds then launches QEMU with OVMF. It will also embed `new.png` into the SimpleFS storage image if that file exists.

    ./run.sh

## Current status and limitations

- The GitHub Actions pipeline builds the normal kernel, the separate DoomGeneric ELF, and the CI-instrumented kernel, then boots VexOS in QEMU and exercises desktop input and applications.
- The first-boot screen is a **non-destructive welcome guide**. It does not partition, format, or install to any disk.
- Storage initialization only mounts recognized FAT32/SFS1 media. Unknown or damaged volumes are rejected without automatic formatting; there is no in-kernel disk formatter yet.
- AHCI support targets SATA controllers. NVMe support is not implemented, and the AHCI driver has not yet been qualified on the user's physical laptop.
- The current boot image is a development image, not a Windows replacement or a dual-boot installer. Do not use it to repartition or overwrite an internal drive.
- A successful QEMU test does not guarantee compatibility with every laptop's firmware, graphics hardware, storage controller, keyboard, or touchpad.

## Notes & warnings
- Large binary artifacts (dist/tiny64.img, dist/storage.img) exceed GitHub recommended sizes; consider using git-lfs or excluding build artifacts from the repository.
